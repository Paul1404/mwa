# AGENTS.md

Guidance for coding agents working in this repository.

## What this project is

MWA is a small, security-sensitive operations app for:

- running Mailcow upgrades over SSH and streaming persisted terminal output;
- planning, reviewing, and applying mail-domain provisioning changes across Route 53, SES,
  and Mailcow.

The stack is Bun, TanStack Start/Router, React, oRPC, better-auth, Drizzle/Postgres, and
Tailwind CSS. Production is a Bun Docker image deployed on Railway.

Read `README.md` before changing behavior. It documents the intended update pipeline,
deployment model, environment variables, and provisioning semantics.

## Repository map

- `src/routes/`: TanStack file-based routes. `_app.tsx` protects the authenticated app shell.
- `src/components/`: shared application and UI components.
- `src/lib/`: browser/SSR clients and shared utilities.
- `src/server/orpc/router.server.ts`: validated API procedures and the main authorization boundary.
- `src/server/runner.server.ts`: the Mailcow SSH update runner, process-local lock, persistence,
  cancellation, and live broadcaster.
- `src/server/provisioning/`: plan construction, provider adapters, and domain apply runner.
- `src/server/db/schema.ts`: Drizzle schema, relations, and persisted status types.
- `drizzle/`: committed SQL migrations and Drizzle metadata.
- `server.ts`: production static-file and TanStack request server.
- `src/routeTree.gen.ts`: generated by the TanStack router plugin; do not edit by hand.

## Setup and common commands

Use Bun; do not introduce npm, pnpm, or yarn lockfiles.

```sh
bun install
cp .env.example .env
bun run db:migrate
bun run dev
```

Local development needs Postgres plus the values documented in `.env.example`. Never commit
`.env` files or real credentials.

Quality checks:

```sh
bun run typecheck
bun run lint
bun run test
bun run build
```

Useful focused commands:

```sh
bun run test -- src/server/crypto.test.ts
bun run test -- src/server/ssh.test.ts
bun run test -- src/server/provisioning/dns-utils.test.ts
```

`bun run lint:fix` and `bun run format` write across the repository. Use them deliberately and
inspect the resulting diff. Biome owns formatting: two spaces, double quotes, semicolons, and a
100-character line width.

## Non-negotiable invariants

### Secrets and authentication

- Private keys, passphrases, Mailcow API keys, and AWS secrets are encrypted at rest with
  AES-256-GCM. Raw secrets must never be returned by an API, rendered after creation, logged,
  placed in audit metadata, or included in thrown errors.
- New procedures that read or mutate operational data belong behind the `authed` oRPC middleware.
  The intentionally public surfaces are better-auth and `/api/health`.
- Keep input validation at the API boundary. Do not trust client-side validation.
- Preserve SSH host-key pinning/TOFU behavior. Host changes invalidate the pinned fingerprint;
  mismatches must fail closed.
- Do not casually change `ENCRYPTION_KEY`. Losing or replacing it makes existing encrypted values
  unreadable. Rotation requires explicit re-encryption or user re-keying.
- Keep `tanstackStartCookies()` last in the better-auth plugin list.

### Mailcow update runs

- The update sequence is intentionally:

  1. `cd /opt/mailcow-dockerized && ./update.sh --force`
  2. `docker system prune -a --force`

- Never add `--gc` to `update.sh`: Mailcow treats it as a standalone cleanup mode and skips the
  update.
- Only one update run may be active in this single-replica deployment. Preserve cancellation,
  terminal status transitions, monotonic per-run log sequence numbers, and persisted logs.
- The request handler must start long-running execution without awaiting it; clients receive the
  run immediately and follow persisted/live events.

### Domain provisioning

- Preserve the plan/review/apply boundary. Planning may observe external state but must not mutate
  Route 53, SES, or Mailcow.
- Apply the reviewed persisted plan; do not silently recalculate a materially different plan at
  execution time.
- Keep provider logic behind the interfaces in `src/server/provisioning/providers/types.ts` and
  instantiate providers through `provider-factory.server.ts`.
- DNS comparison must remain normalization-aware. Add focused tests for changes involving FQDNs,
  TXT quoting/chunking, ordering, DKIM classification, or destructive record changes.
- SES signing is authoritative when enabled: preserve SES Easy DKIM CNAMEs and avoid simultaneous
  Mailcow DKIM signing. Defaults are `eu-central-1` and `default-transactional` unless stored
  provider configuration overrides them.
- Domain runs are locked per domain. Preserve persisted logs, cancellation, and status recovery.

### Database and generated files

- Schema changes require a generated, reviewed, committed migration:

  ```sh
  bun run db:generate
  bun run db:migrate
  ```

- Review both the SQL and `drizzle/meta` changes. Do not use `db:push` as a substitute for a
  migration intended for production.
- Production runs migrations on boot with `src/server/db/migrate.ts`; `drizzle-kit` is deliberately
  absent from production dependencies.
- Do not hand-edit `src/routeTree.gen.ts`. Add, rename, or remove files in `src/routes/` and let the
  TanStack router plugin regenerate it via dev/build.
- better-auth tables are co-located in `schema.ts` and intentionally use the names expected by its
  Drizzle adapter. Treat auth schema changes as compatibility-sensitive.

## Implementation conventions

- Use the `~/*` alias for imports from `src/` and relative imports within a tightly coupled server
  directory when that is clearer.
- Keep server-only modules named `*.server.ts`; do not import secrets, database code, Node/Bun-only
  APIs, or provider SDKs into browser bundles.
- Define oRPC input/output schemas explicitly with Valibot and return serialized DTOs rather than
  database rows containing sensitive columns.
- Record meaningful authenticated mutations through `audit()`, with secret-free metadata.
- Reuse the existing query/mutation patterns and small UI primitives. Match the dark, restrained
  visual system in `src/styles/app.css`; include loading, empty, error, destructive-confirmation,
  and narrow-screen states where relevant.
- Tests live next to the server module as `*.test.ts`. Favor deterministic unit tests; external
  services should be exercised separately rather than becoming required for the default suite.
- Keep dependency families in lockstep. In particular, React/React DOM and their types must not
  drift apart. Dependabot uses the Bun ecosystem and grouped package families; preserve that.

## Verification expectations

Run the checks relevant to the change, and before handing off a substantive change run all four:

```sh
bun run typecheck
bun run lint
bun run test
bun run build
```

Also exercise the changed behavior, not just static checks:

- UI or routing: load the affected route at desktop and narrow widths and check browser errors.
- Auth/API: test signed-out rejection and signed-in success.
- Database: apply the migration to a disposable Postgres database and exercise reads/writes.
- Update runner: use a safe test host; do not trigger a real Mailcow update without explicit scope.
- Provisioning: inspect the rendered plan first and use non-production AWS/Mailcow resources for
  apply tests. Pay special attention to deletes and DKIM changes.
- Deployment: verify `/api/health` and container startup logs, including migrations and the
  encryption boot probe.

If an external integration cannot be exercised, say exactly what was not verified. Never present
unit tests or a successful build as proof that SSH, Mailcow, AWS, Postgres, or Railway behavior was
validated live.

## Change discipline

- Inspect `git status` and existing diffs first. Preserve unrelated user changes.
- Keep changes scoped; avoid opportunistic stack migrations or broad formatting churn.
- Never commit generated secrets, logs, build output, or local environment files.
- Commit messages should explain why the change is needed, not merely restate the diff.
- Do not force-push, amend published commits, or merge without explicit notice and approval.
